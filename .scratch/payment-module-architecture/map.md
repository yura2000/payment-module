## Notes

**Domain**: Flutter + Kotlin, Android-only, white-label Payment Confirmation Module for an interview task. Requirements: `Flutter_interview_task 1.pdf` (repo root). Glossary: `CONTEXT.md` — every session reads it and keeps it sharp.

**Skills every session should consult**: `codebase-design` (modules, interfaces, seams, depth), `domain-modeling` (glossary + ADRs), `grilling` for HITL tickets, `research` for AFK tickets, `prototype` for prototype tickets. Flutter conventions baseline: `flutter-architecture-and-style` (BLoC, get_it locator, exception hierarchy, naming) with the deviations recorded below.

**Non-code deliverables** (out of the decision map, tracked here): prompt log at `docs/ai/prompt-log.md` — this charting session is one of the 2–3 showcased AI interactions; AI Insight Report; two flavor APKs or a demo video. The "add a 3rd brand" recipe (ticket 14) doubles as the report's "how you structured the multi-tenant config" section.

**Demo guidance**: for the Secure path use a *Google Play* AVD system image (release-keys, no root) or a real unrooted device; *Google APIs*/AOSP images are pre-rooted and test-key-signed and will legitimately show Compromised — say so on camera when using one for the Compromised path. The positive screen-recorder case needs an API 35+ device/emulator (Quick Settings *Screen Record* tile). Recording the deliverable video: FLAG_SECURE blanks `adb screenrecord` and MediaProjection recorders — record via the emulator's host-side recorder or an external camera (UNVERIFIED for the emulator recorder; test early).

**Toolchain**: Flutter 3.44.6 via FVM (`.fvmrc`), Dart 3.12.2; `compileSdk`/`targetSdk` 36, `minSdk` 26; Kotlin/AGP as the 3.44 template ships them; Java 17. `flutter` is not on PATH in plain shells — use `fvm flutter`.

**Settled in charting (Rounds 1–2, 2026-09-15)** — the baseline every ticket assumes:

| Area | Decision |
|---|---|
| Scope | Android only: no iOS, no runtime "unsupported platform" adapters. No backend/HTTP: the Foreground Service *is* the simulated processor; the Data layer holds native adapters + in-memory fakes. |
| Vocabulary | Brand = Flavor as a 1:1 invariant (each Flavor ships exactly one Brand, named after it; no runtime switching). In Dart the word is **Brand**; `flavor` appears only in Gradle/CLI. Brands: **Retail** (A), **Utility** (B). |
| User journey | Confirmation page opens → Secure Window on, Security Scan runs once (later re-assessments are silent — ticket 07) → posture gates the Pay CTA per Posture Policy → Pay starts the Payment Job in the Foreground Service, progress mirrored in notification + in-app → Result View on the same route → Secure Window off when the user leaves. Fixed in-memory Payment with Line Items for every brand (Utility renders them). Promo Banner is purely visual. |
| Posture Policy | Per brand, in BrandConfig. Retail: rooted → block, recorder → warn. Utility: both → block. Degrades before Pay → policy re-applies; degrades during the job → job completes, result page shows the warning. |
| Architecture | Strict Clean Architecture, **feature-first, one application package** (revised 2026-09-16 after review — ADR-0001): `lib/core` (Flutter-free shared kernel), `lib/brand_engine` (barrel + `src/`), `lib/features/{security_guard, payment}` (barrel + `src/{domain,data,presentation}` + `di.dart`), composition root in `lib/app`, `lib/brands`, `lib/bootstrap`. Dependency DAG: composition root → all; payment → core, brand_engine, security_guard (barrel only); security_guard → core, brand_engine; brand_engine → core; core → nothing. Module walls and layer rules both enforced by `import_lint` + a regex architecture test. Pub-workspace packages are the named scaling path (ticket 06 research kept for that day). |
| State management | BLoC (`flutter_bloc`). DI: `get_it`, manual `setupLocator()` composing `registerXModule(GetIt)` per package; BrandConfig registered first as a singleton; adapters lazy singletons; BLoCs factories. |
| Errors & model | Exception hierarchy from `flutter-architecture-and-style` (`ServiceException`/`ClientException`/`TransportException`; no `ServerException`) thrown by adapters, caught in BLoCs → failure states. Expected outcomes (Compromised posture, failed job) are sealed **values**, never exceptions. Dart 3 sealed classes + `equatable`, no codegen in the model. Use cases only where a decision or orchestration lives (ticket 13 superseded "one per operation"). |
| White-label engine | Android `productFlavors { retail; utility }` + `--dart-define=BRAND=<id>` read as a `const` → `BrandRegistry` → `BrandConfig`; single `main.dart`; debug assertion that native `BuildConfig.FLAVOR` == Dart `BRAND`; a script/Makefile wraps the pair. BrandConfig is typed Dart `const` per brand (palette, shape, density, motion, typography, copy, capabilities, PosturePolicy; per-feature config looked up by type). Delivered as `ThemeData` + a `BrandTokens` `ThemeExtension` + a `BrandScope` InheritedWidget. Brand slots: capability flags for *behaviour* + a declarative section list for *layout*; `if` on identity is forbidden, `if` on capability is allowed. JSON assets rejected. |
| Native bridge | Hand-written channels — 4 `MethodChannel`s + 2 `EventChannel`s as specified in ticket 10 (no cancel); Pigeon named as the scaling path, not used. Kotlin in-app under `android/app/src/main/kotlin/dev/test/payment/{bridge,security,window,payment,app}/`, one handler class per concern registered by a `ChannelRegistry` from `MainActivity.configureFlutterEngine`. Blocking checks on `Dispatchers.IO`; every `result.*` and `EventSink` emission hops to the main thread through one `MainThreadResult`/`MainThreadSink` wrapper. |
| Animation | `AnimationController.repeat()` as the painter's `repaint:` listenable (paint without rebuild); preallocated Paints; tokens read once; `RepaintBoundary(child: CustomPaint)` in a const-constructible widget outside the `BlocBuilder` subtree; time-based maths for 60/120 Hz parity. Proof: repaint rainbow + DevTools during dev; an integration test asserting frame budgets while the BLoC emits progress at 10 Hz. |
| Verification | Unit tests for use cases; `bloc_test`; per-brand goldens driven from `BrandRegistry`; Dart channel contract tests via `TestDefaultBinaryMessengerBinding`; one Kotlin JVM test for the main-thread wrapper; `mocktail`; `make apk-retail` / `make apk-utility`. |

## Decisions so far

<!-- one line per closed ticket: [title](issues/NN-slug.md): gist -->
- [Root detection approach on Android API 26–36](issues/01-research-root-detection.md): hand-rolled six-signal check set with a ≥2-signal threshold, no RootBeer; all checks on `Dispatchers.IO`; `<queries>` manifest entries required on targetSdk 36; Google APIs/AOSP AVDs legitimately report Compromised. Findings on branch `research/root-detection`.
- [Screen-recorder detection across API levels](issues/02-research-screen-recorder-detection.md): API 35+ `addScreenRecordingCallback` (any MediaProjection, live, fires under FLAG_SECURE; normal permission) — below 35 no official signal, so posture gets an honest third state (shape decided in ticket 07); no unreliable fallbacks. Findings on branch `research/screen-recorder-detection`.
- [Foreground Service compliance on targetSdk 36](issues/03-research-foreground-service-compliance.md): `shortService` (no typed permission, ~3 min cap, `onTimeout` safety net); `POST_NOTIFICATIONS` never gates the job; `startForeground` within 5 s; `IMPORTANCE_LOW` progress notification; template ships AGP 9.0.1 / Kotlin 2.3.20. Findings on branch `research/foreground-service-compliance`.
- [120 Hz rendering on Android with Flutter 3.44](issues/04-research-120hz-android.md): not guaranteed — the engine follows the OS-chosen mode; request `preferredDisplayModeId` via our own window channel (+ `android:appCategory`), assert frame budgets against the live `Display.refreshRate`, prove with `watchPerformance()` + `dumpsys display`. Findings on branch `research/120hz-android`.
- [Cross-layer import enforcement inside a package](issues/05-research-layer-import-lint.md): `import_lint` 2.0.0 (first-party analyzer-plugin system, YAML rules) per feature package; `custom_lint` and DCM rejected; verify at scaffold time; architecture-test fallback. Findings on branch `research/layer-import-lint`.
- [Pub workspace mechanics for a Flutter app member](issues/06-research-pub-workspace-flutter.md): root `workspace:` pubspec + `resolution: workspace` in every member, plain-constraint intra-workspace deps, single root `pubspec.lock` committed (fix `.gitignore`), `pub get` at root *and* in `app/`, tests looped per member via Makefile. Findings on branch `research/pub-workspace-flutter`.
- [Payment state machine](issues/07-grilling-payment-state-machine.md): per-threat Security Posture (Secure / Compromised / **Unverified**), Posture Policy gains `onUnavailable: allow | notice` (Retail allow, Utility notice); one `PaymentConfirmationBloc` with composite state `{payment, posture, verdict, phase}` and sealed phase `Scanning | AwaitingConfirmation | Processing | Completed`; scan lasts ≥ brand `scanMinDuration`, resume re-assesses silently; back blocked only while Processing; retry in, cancel out; result is a view of the same route.
- [Native channel contract](issues/10-grilling-native-channel-contract.md): prefix `dev.test.payment`; 4 MethodChannels (`security.environment`, `window`, `payment.job`, `app`) + 2 replay-1 EventChannels (posture snapshots, job snapshots); `assess()` acks and the stream is the single source of truth; notification permission via `ensureNotificationPermission` inside the adapter; errors → exceptions, `serviceStartFailed`/`timedOut` → values; `ChannelRegistry` owns scope + handlers; shared JSON fixtures for both sides.
- [Payment Job transport + service/engine lifecycle](issues/12-grilling-payment-job-transport-lifecycle.md): process-wide `PaymentJobStateHolder` (`StateFlow`, service sole writer, CAS start); +5 %/250 ms ticker, decline at 60 % for `cents == 99`; final notification detached and kept; terminal snapshots replay until delivered once; notification tap = launcher intent; `START_NOT_STICKY` (process death loses the job — documented); 13-scenario table.
- [Secure Window lifecycle](issues/11-grilling-secure-window-lifecycle.md): `SecureSessionScope` widget + ref-counted `SecureWindowController` over the `SecureWindow` port; route lifetime is the owner ("one lifetime, two owners" with the BLoC's posture subscription); re-assert on resume, errors swallowed and retried; Kotlin stateless; launch gap accepted with reasoning; 8 widget-test scenarios.
- [Brand slot / section-list mechanism](issues/08-prototype-brand-slots.md): **sealed `PaymentSection` hierarchy + `CustomSection(builder)` escape hatch** (closed enum and fixed-skeleton slots rejected); `BrandConfig.features: List<BrandFeatureConfig>` with `feature<T>()` lookup; `PaymentBrandConfig` in `payment/presentation`, `SecurityBrandConfig` in `security_guard/domain`; no capability flags; zero identity conditionals proven by grep; a 3rd brand = one file + one registry line. Prototype on branch `prototype/brand-slots`.
- [Package seams](issues/13-grilling-package-seams.md): per-package interface listing fixed; `BrandId` is a string extension type; **use cases collapsed to where logic lives** (one deep `WatchPostureVerdict`; BLoC uses ports directly — revises Q12); bootstrap adapters (`ChannelDisplayMode`, `ChannelAppInfo`) owned by `app`; private BLoC, public fakes via `testing.dart` entrypoints and registration overrides; `intl` for money; scan view + posture banner in `security_guard/presentation`.
- ["Add a 3rd brand" recipe + guard test](issues/14-grilling-add-a-third-brand.md): 3 mandatory edits (brand file, registry line, Gradle flavor) + optional icon + generated goldens; parametrised `make apk BRAND=`; guard = registry completeness test, flavor↔registry regex test + runtime drift assertion, per-brand goldens (6 states, `golden` tag on Linux CI); doc section, no generator; dev-only brand picker ruled out.
- [Security Scan visual](issues/09-prototype-security-scan-visual.md): **radar**, one token-driven painter (no `scanStyle` config); one sweep == `scanMinDuration`; isolation proven by a canary widget test (60 frames → 0 page-layer paints; control → 60) to be kept in `security_guard`; reduced motion → static frame, same duration. Prototype on branch `prototype/security-scan`.
- [Write docs/architecture.md + ADRs](issues/15-task-write-architecture-spec.md): `docs/architecture.md` (17 sections), five ADRs in `docs/adr/`, six research findings copied to `docs/research/`, glossary confirmed consistent. **Destination reached.**
- **Revision after completion (2026-09-16)**: the Pub workspace was replaced by a single application package, feature-first, at the user's request after weighing pros and cons — see ADR-0001, spec §3–4, and the addenda on tickets 05, 06, 13, 14. Nothing from §5 onward changed.
- **Revision after completion (2026-09-16, #2)**: one composite `PaymentConfirmationBloc` → **two units split on the feature seam** — `SecurityPostureCubit` (security_guard) + a posture-free `PaymentConfirmationBloc` (payment), rules shared only through pure derived functions in the page; Scanning now ends on the timer alone. See spec §7 and ticket 07's addendum.

## Out of scope

- iOS (any native implementation or fallback adapter): the task is Android-only and the user confirmed it.
- Real payment backend / HTTP layer: the task says "simulate".
- Play Integrity API for root detection: needs Google Play + network.
- Runtime Brand switching in release builds: Brand = Flavor is an invariant.
- Cancelling a Payment Job: never asked for, and a `shortService` job of a few seconds has nothing worth cancelling (ticket 07).
- Dev-only runtime brand picker: two flavor APKs are the deliverable; a debug switcher would need `getIt.reset()` + re-registration in the composition root and weakens the Brand = Flavor invariant (ticket 14).
